  Root cause. Reading a memory and referencing it used two different access rules:
  - Reads (memory_get, and the row-level security policy on memories): you can see a memory if it belongs to your tenant, or if it's team-visible and you're an active member of that team.
  - References: you could only use a memory if user_effective_team_access had a row for you and the memory's team. That table is only filled in when access goes through the team-management API (assign_role). Users
    created by raw SQL, including everyone the 0026 backfill provisioned, have no rows there, so they were refused access to their own memories.

  The same faulty check was evaluated in four places:
  - resolve_reference_target, which validates references at write time and is used by memory_write, the async write drain and the plugin SDK.
  - check_hard_delete_with_filtered_citers: your own citers were counted as "inaccessible".
  - memsys_refs_in and memsys_refs_out: your own references were hidden.

  Fix
  - New migration (alembic/versions/0035_2026_06_01_user_can_read_memory.py): adds a SECURITY DEFINER database function, user_can_read_memory(user, memory). It returns true if the memory is in your tenant, or it's
    team-visible and you're an active team member, or you have an existing team-access grant. It doesn't read the tenant setting at all, takes explicit parameters, and doesn't filter out soft-deleted memories, which
    matches the read path.
  - src/mem_mcp/teams/references.py: a new helper, caller_can_read_memory(), wraps that function. All four places above now use it.
  - Unchanged: the not-found and no-access cases still return the same memory_not_accessible error. The three slug lookups (memsys_slug_lookup, and slug lookups in memory_get and memory_get_batch) still check access at
