  Report

  Problem

  Users provisioned via raw SQL (the 0026 backfill pattern) — who have a team_role_assignments row but no user_effective_team_access cache row — could not cite their own memories via references=[{target_uuid,
  reference_kind}]. The references machinery only checked the user_effective_team_access cache (populated by the team-management API or reconciler), which these users never got. A secondary security leak: when team_id IS
  NULL, the old code skipped the access check entirely, making cross-tenant NULL-team memories accessible to anyone.

  Root Cause

  In src/mem_mcp/teams/references.py, all four access-check call sites queried user_effective_team_access only — no owner (memories.tenant_id = caller) check. This missed owner access for raw-SQL-provisioned users, and
  the team_id IS NULL branch in resolve_reference_target silently skipped the check.

  Fix

  New shared access rule (lives in src/mem_mcp/teams/references.py, two functions):

  caller can access memory M iff:
    (1) M.tenant_id = caller_user_id              (owner — matches memory_get's read path)
    OR (2) M.team_id IS NOT NULL
        AND user_effective_team_access row exists for (caller, M.team_id)

  NULL team_id: only (1) can grant access — non-owners are always denied. This closes the leak.

  Two new functions:
  - caller_can_access_memory(conn, *, memory_id, caller_user_id, include_deleted=False) -> bool — single SQL EXISTS query for sites that fetch by memory_id.
  - _caller_can_access_memory_row(conn, *, memory_tenant_id, memory_team_id, caller_user_id) -> bool — row-based variant (Python == for owner check, SQL EXISTS for team access) for sites that already JOIN the memories
    row.
