● I've written the brief to ~/laguna-bench/runs/F1-1/orders/BRIEF.md. It is based on the mind-map design doc, ADRs 0007/0008, the mindmap-driver skill, the current mindmap_* tools (including the newer
  per-branch status work), the team roles, and the web /mindmaps pages.

  It covers what you asked for: the problem and who it's for, 9 user stories, the business rules (work item, states and transitions, permissions, audit trail), 36 numbered acceptance criteria, and an out-of-scope list.
  It contains no schemas, function names or file plans.

  Decisions the brief makes:
  - What a work item is: an existing non-root mind-map node that someone marks as work, one node at a time. It has a kind (story, epic or milestone), a status, and one owner or none.
  - Separate from what's already there: a work item's status is independent of the existing branch status (open/resolved/dropped) and of the map's live/archived state. Resolving a branch or closing a map never changes a
    work item's status.
  - Statuses: todo, in_progress, blocked, done, cancelled, with a fixed list of allowed moves. Cancelling, blocking, reopening or reviving an item needs a reason. Callers can say which status they expect the item to be
    in, and the change is rejected if it doesn't match; this stops one change silently overwriting another.
  - Who may change what: team owners, admins and members can change work items. Viewers and vendors can only read them. People outside the team can't see them at all. The assigned owner must be a team member who can
    write.
  - Audit trail: a history that can't be edited or deleted, recording who, when, before → after, the reason, and whether the change came through the agent or the web UI. The brief lists 8 questions this history must be
    able to answer.
  - Web UI: read-only in v1, so all changes go through the MCP tools.

  Out of scope: epic/story hierarchy and roll-up, un-marking a node, due dates, estimates and priority, notifications, syncing with external trackers, and automatic status changes.

  Open questions for you: I decided these provisionally; they're in section 7 of the brief.
  1. Should work items on an archived map still be changeable? The brief says yes, but no new items can be added.
  2. Can the agent change a status on its own, or only when the person tells it to?
  3. Should the user-facing word be "assignee" instead of "owner"? The existing map vocabulary already uses "owner" for the human side of the conversation, so the two would be easy to confuse.
