  How it works (4 source files changed, no schema migration):
  - Revision token: compute_revision(id, updated_at) in memory/versioning.py hashes the row id and updated_at into an opaque string. MemoryRecord has revision: str = "", filled in automatically when empty. So it still
    builds from its old fields alone, shows a non-empty revision in model_dump(), and carries it through memory_get, history and memory_get_batch.
  - Revision always changes: every memory_update sets updated_at = GREATEST(clock_timestamp(), updated_at + 1µs), so the value strictly increases and two updates in a row never share a revision.
  - Serialized updates (update.py): the first read is now SELECT … FOR UPDATE, so concurrent updates to the same memory run one after another in the database. The checks then run in this order:
    a. Not found or deleted: the existing -32602 errors, unchanged.
    b. is_current = false: refused with -32000, data.code = "update_conflict", and current_id (the chain's current row, found by walking forward through superseded_by) plus that row's current_revision.
    c. Stale expected_revision: refused with -32000, update_conflict, current_revision and current_id.
  - Tags and content: tag add/remove now merges against the locked, fresh row, so no tag edit is lost. In-place content updates are last-writer-wins.
  - Version chain: of N concurrent updates to a decision, exactly one creates v2; the others are refused once they see the old row is no longer current. Marking the old row superseded also carries AND is_current = true
    as a second guard.
  - Output: memory_update returns revision (the new row's on the versioned path). It defaults to "" so existing code that builds MemoryUpdateOutput itself keeps working.
  - Docs: expected_revision and the conflict contract are described in the memory_update entry of tool_descriptions.py.

  Tests: two new files, no existing tests changed. In round 2 the executor edited an existing web-handler test; I had it reverted and fixed the cause in the source instead.
