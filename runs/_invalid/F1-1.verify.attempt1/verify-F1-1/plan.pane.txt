● I wrote the verification plan to ~/laguna-bench/verify/F1-1/VERIFY_PLAN.md. I haven't run any of it, and I wrote it from BRIEF.md, DESIGN.md and CONVENTIONS.md only, since I haven't seen the code.

  It has 42 numbered checks, V1 to V42. Most are marked blocker; any failed blocker fails the round.

  - Project gates (V1–V5):
    - the Alembic migration is the single head and reverses;
    - ruff and mypy are clean on the touched files;
    - the full suite shows no new failures beyond the known red tests;
    - the tenant-scope lint is clean, including a read of every SQL statement in the new service module;
    - the developers' own new tests pass and no existing test was weakened.
  - Schema and database (V6–V9):
    - schema matches the design, with no changes to memories or map membership;
    - the app role cannot update or delete history;
    - row-level security isolates tenants, including when no tenant is set;
    - a user from another tenant gets exactly the same "map not found" response through all four tools.
  - Marking and rejections (V10–V17): each kind, bad kind, root node, already marked, archived map and node not in the map. The node and branch rows must stay byte-identical, and bad assignees are rejected.
  - Status changes (V18–V22):
    - an independently written 25-pair transition matrix, with and without a reason, plus the check order;
    - the expected-status guard;
    - concurrent writes repeated 20 times, with history staying continuous;
    - reason limits.
  - Kind and assignee (V23–V25): kind changes, assign, reassign and unassign, and an assignee who was later removed from the team.
  - Permissions and errors (V26–V31): viewers get a permission error even on bad input, non-members get the opaque response, and archived maps allow changes. Closing a map leaves items alone, error codes follow the
    project's style, and the team_id parameter behaves like the existing tools.
  - History (V32–V38):
    - a randomized 200-operation test that every successful call adds exactly one history row and every rejection adds none;
    - the last history row always matches the current state;
    - the brief's eight audit questions can be answered from the history alone;
    - channel and actor can't be forged;
    - rolled-back changes leave nothing behind, and audit rows carry no content.
  - Registration and regressions (V39–V42): tool registration, scope and descriptions, no regression in existing mind-map tools, and the transition helper tested directly.

  The plan tells the verifier to put its tests under tests/verify/ and to report each check as pass, fail or skipped with evidence. It also says what to treat as out of scope for this round (the list and history tools,
  the mindmap_get embedding, and the web endpoints), so the verifier doesn't fail the developers for work scheduled for round 2. Non-blocker defects escalate to a round fail if there are two or more, or if any one is a
  data-integrity problem.
