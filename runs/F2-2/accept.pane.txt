  F2 — Team workflows for work items (real feature, from Anand's backlog)

  Raw product idea (as written in the backlog — not yet a spec):

  > Mind-map work items exist now, but every team works differently. A team should be able to define
  > its own workflow — the stages a work item moves through, which moves are allowed, and what a move

● I'm rejecting this feature. The acceptance report is at orders/ACCEPTANCE.md; I judged it from reading the code only and didn't run anything.

  The main reasons:

  - Custom stages are blocked by the database. The work_items table still only accepts the five built-in statuses (migration 0046, line 49), and the new migration 0048 doesn't lift that limit. Saving any custom status
    would fail.
  - Items can get stuck. Changing a team's workflow doesn't check items already in progress. An item whose status was removed has no allowed move out of it.
  - Delete is broken. delete_workflow reads result.rowcount, but the database driver returns a plain text status there, so it raises an error. The memsys_workflow_delete tool would therefore always fail.
  - About half the request wasn't built: sign-off from people other than the owner (one or several), the web board, an explanation of why a move is blocked, and a "waiting on me" view. No files under web/ were changed.
  - No tests were added, so none of the above was caught.

  Only two requirements are met, and only in the logic: teams defining which moves are allowed, and requiring a reason for a move. Neither works in practice, because the database rejects any custom status.
