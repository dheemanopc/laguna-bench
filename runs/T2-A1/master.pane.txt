  ## Symptom (as reported)

  From the PMO plugin (it talks to Memsys through the in-process plugin SDK,
  `mem_mcp.plugins`):

  > I write memory M1. `memory_get(M1)` returns it fine. Then I write M2 with
  > `references=[{target_uuid: M1, reference_kind: "cites"}]` and the write is
  > rejected with `memory_not_accessible` ("reference target not found or not
  > accessible"). M1 is mine — same account, I just read it.

  It does not happen for every account. It reproduces reliably for users whose
  account was provisioned the "natural" way — tenant, personal team, owner
  assignment and primary identity created by raw SQL (this is how the 0026
  personal-team backfill provisioned all pre-existing users) — rather than
  through the team-management API. It started after the teams/references work
  landed (migrations ~0024–0026).

  A failing repro is provided:

  working tree). It must pass when you are done.

  ## What we expect

  - A user can always reference (and otherwise act on, via the references
    machinery) memories they can read. Write-time access checks for references
    must agree with the read path — i.e. with what `memory_get` lets the caller see.
  - Find the root cause rather than special-casing the write call. If the
    faulty rule is evaluated in more than one place, every such place must be
    fixed and behave consistently — hidden regression tests cover more than the
    repro.
  - Cross-tenant protection must not regress: referencing another tenant's memory
    that you have no team access to is still rejected with the same **opaque**
    `memory_not_accessible` error envelope (not-found and no-access stay
    indistinguishable).
  - Slug-based lookups that are resolved *before* the target is known
    (`memsys_slug_lookup`, `memory_get` by slug, `memory_get_batch` by slug) gate
    at the team level on purpose — it prevents slug enumeration in teams the
    caller cannot see. Do **not** change those.

  Root cause: the references code decided whether a caller can see a memory using only the user_effective_team_access table. That table is a cache that only gets filled by the team-management API or by a reconciler job
  that runs every minute. Users set up with raw SQL, including everyone the 0026 migration backfilled, have no rows there. So their own memories counted as inaccessible, while memory_get (which only checks ownership)
  returned them fine. The same faulty check ran in four places:
  - the write-time reference check (resolve_reference_target, by UUID and by slug)
  - the citer list shown when a hard delete is blocked
  - the memsys_refs_in tool
  - the memsys_refs_out tool

  Fix:
  - New migration alembic/versions/0035_2026_06_01_memory_readable_by.py adds one database function, memory_readable_by(memory_id, user_id). It returns true when the memory exists, isn't deleted, and the user either owns
    it or has team access to it. It follows the existing SECURITY DEFINER / safe_current_tenant_id() conventions, and a missing user returns false instead of crashing.
  - src/mem_mcp/teams/references.py gets one batched helper that calls this function, and all four places now use it. The reference check no longer skips the access test when a memory has no team.
  - refs_in.py / refs_out.py no longer contain their own SQL.
  - Unchanged on purpose: the team-level slug checks in slug_lookup, memory_get by slug and memory_get_batch by slug. Referencing another tenant's memory without team access still fails with the same opaque
    memory_not_accessible error as a UUID that doesn't exist.

  Tests: I added tests/integration/test_references_memory_readable_by.py with 12 regression tests:
  - reference checks: own memory by UUID, by slug, and with no team; another tenant's memory is rejected with the same error as a missing one, but allowed with team access
  - the hard-delete citer list
  - RefsInTool and RefsOutTool
  - the SQL function itself, including deleted memories, a missing user, and the fallback to the current-tenant setting
  - two SDK end-to-end tests: citing an own memory by slug, and checking that the no-access error matches the not-found error

  No existing tests were changed.

  Verification (run by the executor):
  - alembic upgrade head, then downgrade -1, then upgrade head all worked; the database is now at 0035_memory_readable_by.
  - The repro test, the 12 new tests and the related reference and lint suites: 38 passed.
  - ruff check, ruff format and mypy are clean.
  - Full suite: 37 failed, 1042 passed, 31 skipped, 15 errors.

  Remaining concerns:
  - Baseline not compared: the executor wasn't allowed to run git stash, so it classified each failure from its error message instead (fixtures colliding on hard-coded emails, AWS credentials, leftover rows in the shared
    database, a missing fixture). None of those failures go through the changed code or mention the new migration. The failure count also varied between runs (50 vs 52 failures plus errors), which fits the shared test
    database.
  - Different query counts: a missing target takes one query and a no-access target takes two. That gap existed before the fix and was not changed.
  - Memory with no team: an owner can now pass the reference check for their own memory that has no team. Inserting that reference may then fail because target_team_id can't be null. That gap was already there; it's out
    of scope and not tested.
