  === REQUEST ===
  F2 — Team workflows for work items (real feature, from Anand's backlog)

  Raw product idea (as written in the backlog — not yet a spec):

  > Mind-map work items exist now, but every team works differently. A team should be able to define
  > its own workflow — the stages a work item moves through, which moves are allowed, and what a move
  > needs before it happens (for example a reason, or sign-off from someone other than the owner,
  > possibly from more than one person). Items should never get stuck or lose their history when a
  > team changes its workflow. People need to see and move their team's work on a board in the web
  > app, see why a move is blocked, and see what is waiting on them. Agents must be able to do the
  > same through the MCP tools.

● I've sent the design back for revision and written the review to orders/review-design-1.md. The main reason is that the data model in §1 would not migrate as written.

  1. Schema in §1 is broken:
     - The access policies filter on a team column that four of the new tables don't have.
     - The "from" status can be NULL but is part of a primary key, which Postgres doesn't allow. That breaks how the design marks the statuses an item can start in.
     - The schema-version column defaults to 1 and must be unique per team, so saving a team's second version fails.
  2. "Terminal" statuses contradict today's rules: the design makes done and cancelled terminal (no moves out of them). Today's rules allow done → in_progress and cancelled → todo (work_items.py:45-46), so existing teams
     would not behave exactly as before, which the design promises. Its loop check (edge case E3) would also reject the default workflow.
  3. Blocked moves can't be logged as designed: the move tool raises its error inside the database transaction (mindmap_work_set_status.py:44-60). The rollback throws away the history row and audit entry recording the
     blocked attempt.
  4. History for workflow edits is still undecided: the design defers the choice "to Stage 2", but this document is Stage 2.
  5. Gaps around "waiting on me" and sign-off:
     - The "waiting on me" endpoint is listed in the requirement map but never defined in the web API section.
     - Eligible approvers are described as tenants, while approvals are recorded per person.
     - The bulk rebase option on workflow edit isn't defined, and it overlaps with the per-item rebase tool.
