VERDICT: REVISE

1. Freezing can't work with this schema: `team_workflows` has PK/UNIQUE `team_id` (one row per team), yet `work_items.workflow_id` references `team_workflows(workflow_id)` and editing bumps `schema_version` on that same row (§2 lines 79-82, 108-111, 135-137; §5 line 508). An edit in place rewrites the rules frozen items depend on. Workflow versions need to be immutable rows (or copied on edit), separate from the team's "live" pointer.
2. Cross-tenant writes are not settled. Moving a teammate's card (R9), an approver's decision completing the move, and inserting history rows all hit `work_items_update`/`_insert`, which use `tenant_id = safe_current_tenant_id()` (0046:128-138). Risk 6 (lines 447-450) says updates stay tenant-only "*or*" require membership, without choosing. Which `tenant_id` the history/sign-off rows get is also undecided.
3. The read predicate doesn't follow the existing reader convention. Risk 6 and §5 use UEA, but the memories/team_members read RLS uses `current_user_active_team_ids()` (0033:86-93, 0034:183-186). 0035:18-23 says UEA belongs to the writer (more permissive, refreshed by a reconciler). Also, `can_access_team_resource` is just a boolean function and is usable directly in `USING`. §5 (line 523) is wrong to say otherwise.
4. Rebase scope contradicts itself: "out of scope to call in Stage 2" (line 165) versus "required … in-scope for Stage 2" (lines 376-382). No MCP tool or web endpoint exposes it, so neither agents nor people can do the R4 migration.
5. Minor: the default-workflow seed needs a team row per existing team, and new teams created after 0048 need one too. No creation hook is named in `teams/`.
