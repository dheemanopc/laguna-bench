  ## Symptom (as reported)

  From the PMO plugin (it talks to Memsys through the in-process plugin SDK,
  `mem_mcp.plugins`):

  > I write memory M1. `memory_get(M1)` returns it fine. Then I write M2 with
  > `references=[{target_uuid: M1, reference_kind: "cites"}]` and the write is
  > rejected with `memory_not_accessible` ("reference target not found or not
  > accessible"). M1 is mine — same account, I just read it.

  It does not happen for every account. It reproduces reliably for users whose
  account was provisioned the "natural" way — tenant, personal team, owner
  assignment and primary identity created by raw SQL (this is how the 0026
  personal-team backfill provisioned all pre-existing users) — rather than
  through the team-management API. It started after the teams/references work
  landed (migrations ~0024–0026).

  A failing repro is provided:
  `tests/integration/test_references_own_memory_repro.py` (already in your
  working tree). It must pass when you are done.

  ## What we expect

  - A user can always reference (and otherwise act on, via the references
    machinery) memories they can read. Write-time access checks for references
    must agree with the read path — i.e. with what `memory_get` lets the caller see.
  - Find the root cause rather than special-casing the write call. If the
    faulty rule is evaluated in more than one place, every such place must be
    fixed and behave consistently — hidden regression tests cover more than the
    repro.
  - Cross-tenant protection must not regress: referencing another tenant's memory
    that you have no team access to is still rejected with the same **opaque**
    `memory_not_accessible` error envelope (not-found and no-access stay
    indistinguishable).
  - Slug-based lookups that are resolved *before* the target is known
    (`memsys_slug_lookup`, `memory_get` by slug, `memory_get_batch` by slug) gate
    at the team level on purpose — it prevents slug enumeration in teams the
    caller cannot see. Do **not** change those.

  Root cause. Four places that decide "can this user see memory M" only checked the user_effective_team_access table. That table is filled only by Python code (the team-management API and a periodic reconciler job).
  Users provisioned by raw SQL, like the 0026 backfill did, have no row in it for their own personal team. memory_get doesn't use that table at all: it returns any memory whose tenant_id is the caller's. So writes
  rejected references that reads allowed. The same lookup also skipped the access check entirely when the target memory had no team, which let anyone reference such a memory across tenants. That gap is now closed.

  Fix (6 files):
  - alembic/versions/0035_2026_10_15_memory_readable_by.py adds one SQL function, memory_readable_by(memory_id, user_id), written to the house style for these helpers (SECURITY DEFINER, fixed search_path, execute granted
    to mem_app). It returns true if the memory belongs to the user's tenant, or if the user has team access to the memory's team. A NULL user gets false. It takes the user as an argument, because every caller runs
    without a tenant set.
  - src/mem_mcp/teams/references.py adds can_read_memory and can_read_memory_bulk, which call that function. All four places now use them:
    - resolve_reference_target (the write path). Not-found and no-access still produce the same opaque error.
    - check_hard_delete_with_filtered_citers.
    - refs_in.py (memsys_refs_in).
    - refs_out.py (memsys_refs_out), which now checks each target memory rather than the team ID stored on the reference row.
  - The function deliberately doesn't filter soft-deleted memories, because memory_get returns them too. The reference write path still rejects deleted targets in its own lookup.
  - The slug-based lookups, which check access at team level on purpose, are unchanged.
  - Tests: 15 new regression tests, 9 in tests/unit/test_references_own_memory.py and 6 in tests/integration/test_references_own_memory.py. No existing tests were modified. They cover:
    - the access function's rules;
    - resolving a reference to your own memory, and the opaque error for a deleted target;
    - the filtered citer list on hard-delete;
    - both reference-listing tools, own versus foreign;
    - a cross-tenant write rejected with exactly the same error as a nonexistent UUID, with no memory row created;
    - a cross-tenant write that succeeds when team access has been granted.
